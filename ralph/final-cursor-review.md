## Findings, regressions, and gaps

1. **Local Electron-smoke build trap (not a regression, but worth calling out again).** Running `npx playwright test --config=playwright.electron.config.ts` right after `remix dev` (or any dev-mode build) leaves `build/index.js` in dev/jsxDEV form; `electron/main.cjs` starts the embedded server with `NODE_ENV=production`, which cannot execute that dev build, so every Electron smoke spec times out waiting for the Home heading with a misleading "heading not visible" error rather than the real SSR 500. This is already known and documented (`ralph/qa-report.md` finding 1, task #10 dev notes) and is correctly mitigated in CI (`.github/workflows/pr.yml`'s `electron-smoke` job runs `pnpm run build:remix` immediately before `pnpm run test:e2e:electron`), but there is no guard (e.g., a `pretest:e2e:electron` script or a runtime check in `electron/main.cjs`/`server/index.js` that fails fast with a clear message when the build's runtime doesn't match `NODE_ENV`) protecting a human running the electron suite locally without first rebuilding. Recommend either wiring `build:electron`'s dependency into `test:e2e:electron` via an npm `pre*` script, or having `server/index.js` detect a jsxDEV-only build under `NODE_ENV=production` and fail with an actionable message instead of a generic 500.

2. **Doc/testid drift (cosmetic).** `docs/epics/epic-005-next-cycle-fixes.plan.md`'s Item D coverage table says the placement is asserted via `data-testid="on-program"`; the actual code and test use `data-testid="program-thumbnail"` inside `data-testid="presentation-controls"`. Code and test agree with each other; only that one doc line is stale. No functional impact.

3. **better-sqlite3 native binding not prebuilt for this environment's Node (v24.4.1 / darwin arm64).** The Remix dev server fell back to the JSON-file library store during my Remix e2e run ("SQLite unavailable ... better-sqlite3: Could not locate the bindings file ... falls back to poster.library.json"). This is a documented, intentional fallback (see `requirements.md` §4: "Driver selection (better-sqlite3, fallback node:sqlite, then JSON file fallback)"), not a code defect, and CI explicitly runs `pnpm rebuild better-sqlite3` before tests. Noting it here only because a reviewer/operator hitting the same thing locally could mistake the JSON-fallback log line for a bug; it isn't one, and the Electron smoke run (task 6 above) used the same environment and still passed 8/8 (Electron's `startServer` runs the app under Electron's own Node ABI via `ELECTRON_RUN_AS_NODE=1`, and the JSON fallback is exercised safely in the affected specs).

I did not find any commit claim that the code does not back up — task #9's "packaged/Electron acceptance evidence" and task #10/#11's "native folder picker fix + real-button guard" claims all reproduce cleanly on this HEAD.
